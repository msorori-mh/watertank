# الإسناد التلقائي — مرحلة مرشحة للاختبار

Baseline: `main@8dcd68ea4d08297cfc294d46006f61058daba8c5`.

الحالة: غير مفعل إنتاجيًا. لا يُعد هذا الفرع إصدارًا جاهزًا للهاتف.

## السلوك المقترح في الكود

- الطلب النقدي الجديد يبقى pending وقابلًا للإلغاء أثناء البحث. تفعيل الإسناد يعني تجاوز الاعتماد الإداري لهذا المسار؛ يجب اعتماد هذا التغيير التشغيلي قبل التفعيل.
- سائق معتمد، نشط، متاح، في المدينة نفسها، سعة مطابقة ونوع ماء يحدده السائق، وموقع آخر تحديث له خلال 90 ثانية.
- ترتيب بالمسافة الجغرافية التقريبية، لا بزمن الطريق. لا يوجد تحقق من مصدر الماء أو امتلاء الوايت في هذه المرحلة.
- عرض حصري لسائق واحد لمدة تصل إلى 60 ثانية. رفض أو انتهاء المهلة ينقل العرض للمرشح التالي، بحد أقصى ثلاثة عروض أو 180 ثانية للبحث.
- لا يوجد مرشح؟ ينتظر الطلب حتى نهاية مهلة البحث ثم يظهر في قائمة التدخل اليدوي بلوحة الطلبات. لا تعني هذه الحالة أن موظفًا تسلم الطلب فعليًا.
- قبول الطلب يتحقق مجددًا من صلاحية العرض والسائق ثم يسند الطلب ذريًا. قيد فريد يمنع وجود طلبين نشطين للسائق نفسه، بما في ذلك المسارات القديمة واليدوية.
- الواجهة تحدث الموقع كل 30 ثانية والعروض كل 5 ثوانٍ أثناء فتح التطبيق. لا يوجد في هذا الفرع تسليم إشعار push في الخلفية، أو ضمان عمل الاتصال أثناء إغلاق الشاشة.
- شاشة العميل تعرض حالة البحث أو انتظار الإسناد اليدوي. تحديد موقع العميل يستخدم Capacitor مع مهلة 15 ثانية وخيار اختيار نقطة على الخريطة يدويًا؛ الإذن نفسه يتطلب تفاعل المستخدم.

## الملفات والاختبار

`db/auto_dispatch_candidate.sql` مسودة قاعدة بيانات وليست migration منشورة. جداولها خاصة وسياسات RLS تمنع القراءة المباشرة. RPCs العامة مقيدة بالمستخدم أو المسؤول. إعداد الخادم `enabled=false` وعلم الواجهة `VITE_AUTOMATIC_DISPATCH` غير مفعلين افتراضيًا.

اختبار SQL معزول باستخدام PGlite 0.5.8:

```sh
node scripts/test-dispatch-candidate.mjs /absolute/path/to/pglite/dist/index.js
npx tsc --noEmit
```

الاختبار يستخدم جداول fixtures مصغرة؛ لا يثبت توافق جميع triggers وسياسات قاعدة الإنتاج ولا تنافس اتصالات PostgreSQL المستقلة.

نتائج هذه الجولة: نجحت 17 مقارنة SQL، وفحص TypeScript، وعقدا Google Auth والدفع النقدي. بناء أصول Android توقف تقدمه عند prerender مع `Concurrency: 0` ولم يكتمل؛ لا يوجد APK أو AAB جديد لهذه الميزة، ولا نتيجة CI لهذا الفرع حتى الآن. تثبيت الحزم المحلي كان عبر npm دون إنشاء lockfile جديد؛ يجب إعادة البناء بالتثبيت المقفل المعتمد في CI.

## المتبقي قبل التفعيل

تحديث 2026-09-15: اكتمل بناء أصول Android محليًا ومزامنة Capacitor بعد ضبط `prerender.concurrency=1`؛ البيئة كانت تبلغ عن صفر معالجات. فحوص Semgrep/Gitleaks/Trivy للالتزام `844bbf9` نجحت في GitHub، بينما توقف Android عند إعداد SDK بسبب الحزمة القديمة `tools`. عُدّل الإعداد ليطلب `platform-tools`، مع الإبقاء على تثبيت API 36 وأدوات البناء. لا يعني نجاح أصول الويب نجاح APK أو اختبار الهاتف. اتصال Supabase المتاح ما زال لا يعرض مشروع وايت ماء.

1. الوصول إلى مشروع وايت ماء الصحيح `actynnctmmyysocqxwdi` المدار عبر Lovable؛ لا تستخدم أي مشروع Supabase آخر.
2. إنشاء migration مؤرخة بواسطة CLI من الملف المرشح، وتطبيقها أولًا على بيئة اختبار بنسخة schema الحالية. التحقق من عدم وجود طلبات نشطة متعددة للسائق قبل إنشاء القيد الفريد، ومن فهارس الاستعلامات وEXPLAIN عند حجم بيانات واقعي.
3. اختبار التنافس الحقيقي: قبولان متزامنان، قبول مقابل إلغاء/إسناد يدوي، تعطيل السائق، توقف العامل وإعادة تشغيله، وصلاحيات العميل/السائق/المسؤول باستخدام JWT حقيقية.
4. إعداد عامل مجدول محمي يستدعي `dispatch_private.tick()` كل خمس ثوانٍ. لا تُمنح هذه الدالة للعميل. راقب تأخر العامل والطلبات العالقة؛ لا توجد جدولة في هذا الفرع.
5. تنفيذ واختبار إشعارات عروض السائق على هاتف حقيقي، خصوصًا الخلفية وقفل الشاشة. لا تفعّل الإسناد العام قبل ذلك، أو احصر تجربة مراقبة بوضوح في السائقين الذين يبقون التطبيق مفتوحًا.
6. مراجعة خصوصية تحديث موقع السائق وإفصاحات الموقع. بيانات آخر موقع داخل الجدول الخاص لا تتضمن سجل حركة؛ تحقق من أن سياسة حذف الحساب الإنتاجية تحذف سجل السائق وبالتالي موقعه وعروضه المرتبطة.
7. اختبار تحديد الموقع يدويًا وGPS، ورفض الإذن وضعف الشبكة، على APK موقّع قبل تسليم الإصدار. ارفع versionCode واستخدم مفتاح الرفع الحالي.
8. توليد أنواع Supabase الرسمية واستبدال حد RPC المؤقت في `src/lib/dispatch.ts`، ثم بناء الواجهة بعلم `VITE_AUTOMATIC_DISPATCH=true` لبيئة التجربة فقط.

## الإيقاف

تعطيل `dispatch_private.config.enabled` يمنع قبول العروض الجديدة فورًا؛ دورة العامل التالية تغلق العروض وتحيل البحث الجاري إلى يدوي. الطلبات المقبولة تواصل رحلتها. راجع الطلبات العالقة يدويًا إذا كان العامل نفسه متوقفًا. لا تحذف جداول التدقيق عند الإيقاف، ولا تنشئ مفتاح توقيع جديدًا.
